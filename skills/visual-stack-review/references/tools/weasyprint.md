# WeasyPrint — Deep Dive

**Version at time of writing:** WeasyPrint 61.x  
**License:** BSD (open source, free)  
**Language:** Python  
**Install:** `pip install weasyprint`

**⚠️ Version sensitivity:** The matrix ratings in `visual-stack-review/SKILL.md` assume WeasyPrint **≥ v60** (released November 2023). WeasyPrint v60 substantially rebuilt SVG support (replaced cairosvg with a new engine) and improved named-string/running-element support for running headers. If you are on WeasyPrint < v60, treat Running headers/footers as ★★★☆☆ and SVG as ★★☆☆☆. Upgrade before evaluating against the matrix. Known remaining limitations even on v60+: SVG `<use>` with deeply nested transforms can still mis-render; multi-level running headers with chapter-and-section context simultaneously require workarounds.

---

## What WeasyPrint actually is

WeasyPrint is a Python library that converts HTML+CSS to PDF using its own layout engine — not a browser. This is the fundamental difference from Paged.js/Puppeteer: it interprets CSS itself rather than delegating to Chromium. This means it gets some things right that Chromium gets wrong for print (e.g. CSS Paged Media support without a polyfill), and gets some things wrong that Chromium gets right (e.g. modern CSS features like `grid` subgrid, `container queries`).

---

## Quality ceiling for designed documents

**Honest ceiling:** WeasyPrint produces clean, professional PDFs that will satisfy most business document needs. The ceiling is hit when:
- You need complex multi-column layouts with intricate absolute positioning
- You need JavaScript-driven content (charts, dynamic SVGs rendered from JS libraries)
- You need pixel-perfect brand output with complex blending modes or layer effects

For report-style documents (tables, text columns, simple figures), WeasyPrint's output quality is excellent and often superior to Paged.js (more reliable pagination, better table handling).

## What WeasyPrint is genuinely good at

**Tables.** WeasyPrint handles multi-page tables significantly better than Paged.js. `thead` repeats correctly on each page, `break-inside: avoid` on rows is reliable, and column widths are stable. This is the single biggest practical advantage over Paged.js for data-heavy documents.

**Simple to medium CSS layouts.** If your document uses flexbox for column layout and doesn't require complex grid positioning, WeasyPrint renders reliably. What you write in CSS is what you get in the PDF.

**Running headers and footers.** CSS Paged Media `@top-left`, `@bottom-center`, etc. work natively and reliably. `string()` and `running()` functions for pulling page titles into headers work as specified.

**Widow/orphan control.** `orphans` and `widows` CSS properties are implemented and work. Paged.js treats them inconsistently.

**Python integration.** If your data pipeline is in Python (Django, Flask, FastAPI, scripts), WeasyPrint integrates in 3 lines. No Node process, no subprocess calls, no browser management.

**Predictable rendering.** WeasyPrint renders the same way every time, on every machine, without browser version drift. Puppeteer/Paged.js can produce slightly different output when Chrome updates.

## Where WeasyPrint loses to alternatives

**Modern CSS coverage.** WeasyPrint does not implement CSS Grid Level 2 (subgrid), container queries, `@layer`, or several other modern CSS features. If your HTML was designed for browser display with modern CSS, you may need to rewrite significant portions for WeasyPrint compatibility.

**No JavaScript.** WeasyPrint does not execute JavaScript. This means:
- Charts generated by Chart.js, D3, Recharts, etc. will not render — you need static SVG alternatives
- Any content that relies on JS to render (React components, dynamic tables) must be pre-rendered server-side

**Font handling.** WeasyPrint requires fonts to be explicitly installed or available at render time. WOFF2 web fonts are supported but need explicit `@font-face` declarations. If your CSS references Google Fonts CDN URLs, WeasyPrint will attempt to fetch them at render time — this may be slow or fail in CI environments. Best practice: vendor all fonts locally.

**Complex absolute positioning.** Intricate layouts with many `position: absolute` elements at precise coordinates can produce unexpected results. WeasyPrint's handling of `z-index` and stacking contexts is less reliable than Chromium.

**SVG support.** Basic SVGs render correctly. Complex SVGs with filters, gradients, or animations may render differently than in a browser. Always test SVG assets in WeasyPrint specifically.

**CSS specificity edge cases.** WeasyPrint's CSS inheritance and specificity implementation has edge cases that differ from browser behaviour. If you copy CSS from a browser-targeted stylesheet, expect to debug some style issues.

## Common pain points and how to fix them

**Font not loading (renders in Times New Roman)**  
Root cause: `@font-face` URL is relative and WeasyPrint can't resolve it, or the font file is missing.  
Fix: use `base_url` parameter in `weasyprint.HTML(filename='...', base_url='/path/to/assets/')`, or convert all `@font-face` URLs to absolute paths.

**Page background not filling to edge**  
Root cause: `background-color` on `body` or `html` does not fill the page margin boxes.  
Fix: use `@page { background-color: ... }` instead, or set `margin: 0` on `@page` and manage margins in the content area.

**Table overflows off the page**  
Root cause: `width: 100%` on a table inside a container with horizontal padding causes the table to exceed page width.  
Fix: use `max-width: 100%` on tables, or use `box-sizing: border-box` throughout.

**Images too large**  
Root cause: images without explicit dimensions are rendered at their natural pixel size, which may exceed the page.  
Fix: `img { max-width: 100%; height: auto; }` in your print CSS.

**Footnotes not working**  
Root cause: CSS `float: footnote` is a Paged Media spec feature that WeasyPrint supports partially. Complex footnote layouts (multi-column footnotes, footnotes with images) may not render correctly.  
Fix: for complex footnotes, consider rendering them as body content at the end of each section rather than as true CSS footnotes.

## Migration cost: from Paged.js to WeasyPrint

**Effort: Medium**

**What changes:**
- Remove all `<script>` tags for Paged.js and its polyfill — no JavaScript runs
- Audit every CSS rule for browser-specific features (grid subgrid, container queries, custom properties that depend on JS) and replace with WeasyPrint-compatible equivalents
- Replace all JavaScript-rendered charts/figures with static SVG equivalents
- Rebuild the build pipeline: `pagedjs-cli input.html -o output.pdf` becomes `weasyprint input.html output.pdf` or a Python script
- Vendor all fonts locally (no CDN font loading in WeasyPrint)

**What you keep:**
- HTML structure (unchanged)
- Most CSS (flexbox layouts, typography, colors, spacing)
- CSS Paged Media rules (`@page`, running headers/footers) — WeasyPrint supports these natively
- Content

**One-time vs ongoing:**  
One-time migration cost for CSS cleanup and chart replacement. Ongoing authoring is similar — still writing HTML+CSS. Build pipeline change is one-time.

**Risk areas:**
- Any document using JS-rendered charts or dynamic content needs static alternatives first
- Complex grid layouts may need significant CSS rewriting
- Font loading needs explicit setup in WeasyPrint

---

## Migration cost: from WeasyPrint to Paged.js

**Effort: Low-Medium**

**What changes:**
- Add Paged.js script tag to HTML, or use pagedjs-cli
- May need to add `.page` class wrappers to section elements for fixed-layout pages
- Tables will need more careful testing — Paged.js table pagination is less reliable
- Build pipeline: Python WeasyPrint call → Node pagedjs-cli command (or headless Chrome subprocess)

**What you keep:**
- HTML structure
- Most CSS (Paged.js runs in Chromium so modern CSS features work)
- CSS Paged Media rules (Paged.js polyfills these)

**Risk areas:**
- Table pagination regressions (test all multi-page tables carefully)
- Background fills may need the `.pagedjs_page` selector workaround (see visual-review/references/pagedjs.md PJ-1)
- Orphan `border-top` bugs on continuation pages (see PJ-3)

---

## When to choose WeasyPrint

- Python ecosystem
- Data-heavy documents with complex tables
- Predictable server-side rendering in CI/CD
- No JavaScript-dependent content
- You want a simpler build pipeline (one process, no browser)
- Your document doesn't use modern CSS features introduced after ~2020
